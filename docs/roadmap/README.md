# VAYA Implementation Roadmap

This is the status tracker and index for the phased roadmap produced by the 2026-08-19 codebase audit (`docs/product/audit.md`). Each phase is independently understandable and sized to be executable in one Claude Code session — a future session should be able to say **"Implement Phase N"** and act on that phase's file alone, without rediscovering the product from scratch.

## How to use this document

- Read `docs/product/audit.md`, `docs/domain/model.md`, `docs/domain/ride-engine.md`, and `docs/domain/pricing.md` once, at the start of a roadmap session, for the shared context every phase assumes.
- Each phase file (`phase-NN-slug.md`) is self-contained: objective, prerequisites, exact scope, flows, screens, UX behavior, design-system work, frontend/backend/database/API changes, business rules, testing, analytics, Definition of Done, dependencies, risks, complexity.
- Update the status table below as phases complete — this is the single source of truth for "what's done."

**Phase 11 notes:** Built the first consuming logic for the `recurring_patterns` table (`detected → suggested → enabled` lifecycle, already correctly modeled since the original audit but with zero consuming logic before this phase). **Detection is a background job, reusing Phase 7's one BullMQ queue as a second job type** (`recurring-pattern-scan`, routed by `job.name` in `apps/api/src/worker.ts` alongside the existing `dispatch` job type) rather than a second queue — CLAUDE.md's explicit "one minimal queue... until a second genuinely distinct use case justifies more" rule is honored by extending, not duplicating. Installed as a BullMQ repeatable job via `Queue.upsertJobScheduler` (`apps/api/src/lib/queue.ts`) — the originally-planned `Queue.add({repeat})` option no longer exists on this installed BullMQ major version (6.x), discovered at typecheck time, not assumed; `upsertJobScheduler`'s idempotent scheduler-id semantics are the direct replacement. Detection-algorithm logic is pure/testable (`packages/domain/src/recurring/detect-recurring-patterns.ts`): clusters a user's ride/booking history by corridor (a local haversine helper, since `packages/domain` cannot depend on `apps/api`) and scores each cluster's `confidenceScore = tripCountFactor * 0.6 + timeConsistencyFactor * 0.4`.

**Detection-threshold config shape** (mirroring Phase 6's `pricing_configs` pattern exactly, per this phase's explicit business rule): a new `recurring_detection_configs` table (migration `0010_magenta_molly_hayes.sql`, additive), one active `global`-scope row read by `recurring-config.service.ts` and mapped onto `@vaya/domain`'s pure `RecurringDetectionConfig`, falling back to `DEFAULT_RECURRING_DETECTION_CONFIG` if no row exists — same never-blocks-the-caller posture `getActivePricingConfig` established. Seven tunables: `minTripCount` (3, matches the phase doc's own example prompt copy), `fullConfidenceTripCount` (6), `lookbackDays` (60), `corridorRadiusMeters` (1200), `timeWindowMinutes` (60), `suggestedConfidenceThreshold` (0.6, the detected→suggested promotion cutoff), and `dismissalRequiredConfidenceDelta` (0.15). Full derivation reasoning for each: `packages/domain/src/recurring/default-recurring-detection-config.ts`'s doc comment.

**Dismissed-pattern re-suggestion rule** (this phase's other required business decision): chose "require materially stronger evidence," not permanent suppression — and found a way to implement it **without adding a trip-count column** to `recurring_patterns` (the phase doc's Database section explicitly scoped "no new tables," and a new column felt like unnecessary schema growth for a signal already implicit elsewhere): `confidenceScore` is never cleared on dismissal, so it's already a durable "evidence level at dismissal" baseline; a later scan only resurrects the row if its freshly recomputed `confidenceScore` clears the old one by `dismissalRequiredConfidenceDelta`. Full reasoning: `packages/domain/src/recurring/should-resuggest-after-dismissal.ts`.

Driver auto-draft (enabled driver pattern → same-day draft → explicit confirm → publish) **reuses the existing ride-creation endpoints outright** — `POST /rides` gained an optional `recurringPatternId` (validated server-side: must belong to the caller, be an `enabled` **driver** pattern, or the request is rejected, proven by a dedicated integration test) rather than a bespoke "confirm auto-draft" endpoint; the mobile confirmation screen (`app/recurring/confirm-draft.tsx`) is deliberately a single lightweight screen, not the full 3-step `driver/publish.tsx` flow — it reuses only the price step's shape (`PriceRangeStepper`, pre-filled at the server's `recommended`) and skips candidate-stop selection entirely, since publishing with zero additional stops is already a fully valid choice in this codebase. Rider proactive-matching **extends `matching.service.ts`** with `findBestMatchForRecurringPattern` (reuses the existing `searchRides`/`scoreCandidates` ranking and pickup-viability logic verbatim — no parallel matching implementation), called from `recurring.service.ts`'s `checkProactiveMatchesForEnabledRiderPatterns` for every `enabled` rider pattern, gated by a 12h `lastMatchedAt` cooldown so the same match doesn't re-notify on every scan tick. Both detection and proactive-matching run inside the *same* periodic job (folded into one `recurring-pattern-scan` job rather than two), since both are periodic recurring-pattern maintenance on the same cadence — documented in `recurring.service.ts`'s `runRecurringPatternDetectionScan` doc comment.

API: `GET /recurring-patterns` (mine — includes computed, non-stored `matchesToday`/`todayRideId` fields for an enabled driver pattern, so the mobile management screen/prompt never re-derives day-of-week logic itself) and `PATCH /recurring-patterns/:id` (`{action: 'enable'|'dismiss'}`, enforced through a new `canTransitionRecurringPatternStatus` state machine in `packages/domain`, mirroring `ride-status.ts`'s pattern — the authoritative-state-machine-in-domain rule applied to a fourth entity). Notifications: `recurring_pattern_detected`/`recurring_proactive_match` — already-modeled event types from Phase 7 that had never been dispatched by anything before this phase — now fire via the existing `notifyBestEffort`/BullMQ path, with real French body copy added to `notifications.service.ts` (previously falling through to the generic default).

**Phase 10 notes:** Built the cancellation/no-show flow that didn't exist anywhere before this phase (`docs/product/audit.md` §1's "Cancellation flow UI — MISSING"), with an explicit, reputation-based policy — full design and reasoning in `docs/domain/cancellation-policy.md` — since VAYA has no payment system to build a BlaBlaCar-style refund policy against. **Policy tiers** (`packages/domain/src/booking/cancellation-policy.ts`, pure and unit-tested): ≥24h before departure is free (no consequence); <24h but ≥30min is "moderate" (+1 reliability penalty point, no rating impact); <30min or after departure is "severe" (+3 points). A separately-reported **no-show** (not a cancellation tier) is weighted heavier still — +5 points and an automatic 1-star rating for the no-show party, inserted via Phase 9's rating mechanism (`ratings.service.ts`'s new `recordAutomaticNoShowRating`) — and can only be reported once `packages/domain`'s `canReportNoShow` confirms at least 15 minutes have passed since `departureAt` (server-enforced, independent of the mobile UI's contact-first guidance text). New `reliabilityPenaltyPoints` integer column on both `driver_profiles` and `rider_profiles` (migration `0009_nasty_boomerang.sql`, additive) — deliberately *not* reusing `reliabilityScore`, which Phase 9's rating-aggregate recompute would silently overwrite on the next rating submission; a raw point count, not a fabricated normalized score, honest about being a first-cut signal pending real volume to tune against.

**A second seat-accounting race this phase found and fixed, beyond its own scope's obvious ask**: `cancelBooking` (Phase 1 through 9) guarded its status transition only against a stale pre-read via `canTransitionBookingStatus`, then updated the booking row unconditionally by id — two concurrent cancel attempts on the *same* booking (e.g. rider and driver racing to cancel at once) could both pass that check and both restore a seat, double-crediting `rides.seatsAvailable`. Fixed by re-validating `status` inside the `UPDATE ... WHERE` clause itself (`WHERE id = :id AND status = :expectedStatus`), the same atomic-conditional-update discipline Phase 1's `acceptBooking` fix established for the decrement side — applied to both `cancelBooking` and the new `reportNoShow`. Proven by a concurrent-cancel integration test mirroring Phase 1's original race test.

API: `GET /bookings/:bookingId/cancellation-preview` (read-only tier/consequence preview, so the mobile confirmation sheet shows the consequence *before* the destructive action — the phase doc's explicit UX requirement) and `POST /bookings/:bookingId/report-no-show` are new; `POST /bookings/:bookingId/cancel` (pre-existing route, previously with no UI ever calling it beyond `(tabs)/trips.tsx`'s instant unconfirmed tap) now returns the applied `cancellationPolicy` alongside the booking. Both new mutations reuse `cancelBooking`'s existing atomic seat-release pattern rather than duplicating it. Notifications: two new event types, `booking_cancelled` and `booking_no_show_reported` (`packages/domain`'s notification-event enum, `notifications.schema.ts`, mobile's `NotificationEventType` union and `notificationCopy.ts`), dispatched to the *other* party only via Phase 7's existing `notifyBestEffort`/BullMQ path.

Mobile: `CancellationSheet` and `NoShowReportSheet` (`apps/mobile/src/features/bookings/`, both `BottomSheet`-based, no new design-system primitive per the phase doc's explicit scope) are shared components wired into every active-booking screen that exists today — `(tabs)/trips.tsx` (replacing its old instant, unconfirmed `cancelBooking(booking.id)` tap), and `bookings/pending.tsx`/`pickup.tsx`/`live.tsx` (new "Annuler" affordances; `live.tsx` also gets the no-show reporting button, plus a fix to its presentational 4s auto-advance-to-settlement timer so it no longer fires out from under an open sheet). **Deliberately rider-only at every entry point** (documented in `docs/domain/cancellation-policy.md`, not silently assumed): this codebase still has no driver-side per-booking screen at all, the same gap Phases 7, 8, and 9's notes already flagged — the backend supports either party equally, only the mobile wiring is one-sided today. Pure helper logic (`cancellationHelpers.ts`: tier→Badge-variant mapping, minutes-until-departure formatting, the analytics payload builder) is unit-tested; the sheets themselves get a source-level regression test (same "no RN render harness in this repo" constraint every prior phase's notes document) proving the confirm action is gated on the real server preview and that the destructive mutation only fires from the confirm handler. Both analytics events (`booking_cancelled` by role/tier-as-time-bucket, `no_show_reported` by role) fire via the existing `trackEvent` hook.

Tests: 13 domain unit tests for `computeCancellationPolicy`/`canReportNoShow` across the timing boundaries (inclusive at both the 24h and 30min edges, and the no-show grace-buffer edge); a real-Postgres integration suite (`apps/api/src/modules/bookings/__tests__/bookings-cancellation.integration.test.ts`) covering the full cancel flow (status, other-party notification, reliability penalty, atomic seat release), the concurrent-double-cancel race fix, the no-show-before-departure rejection, and the full no-show flow (status, seat release, automatic rating, penalty, notification); 2 new trip-status-transition unit tests for the widened `no_show` edges.

**Phase 9 notes:** Closed the loop on the already-correctly-shaped `ratings` table with a real submission flow, aggregation, and trust-tier surfacing. **Necessary scope addition, verified before building (not assumed from the phase doc)**: this codebase had no trip-completion mechanism at all — confirmed directly (no caller of `canTransitionTripStatus` existed anywhere outside `packages/domain`'s own tests before this phase; Phase 8's notes above already flagged this). Added the minimal trigger only: `POST /trips/:id/complete` (new `apps/api/src/modules/trips` module) transitions a trip to `completed` via `packages/domain`'s state machine, which now allows a direct `completed` edge from every non-terminal trip status (`trip-status.ts`), not only from `arriving` — since this app's trip-progress screens (`bookings/pending → pickup → live → settlement`) are still a presentational mock with no live position feed driving them through the intermediate statuses one at a time. Deliberately callable by **either** trip party (not driver-only as a literal reading of the phase doc suggested): there is still no driver-side trip-execution screen anywhere in this codebase, so driver-only would leave the endpoint uncallable from any real screen; mirrors `bookings.service.ts`'s existing `cancelBooking`, which already lets either party trigger a status transition. Completing a trip also transitions its `booking.status` to `completed` (another existing-but-never-set schema value) and recomputes both parties' `tripCount` from `trips` directly (not an incremented counter) — a second, related gap this phase found: `driver_profiles.tripCount` was previously written only by `seed.ts` and never updated by any real trip.

**Rider-reputation storage decision** (this phase's other required, previously-open call): implemented a dedicated `rider_profiles` table (migration `0008_yellow_shen.sql`) mirroring `driver_profiles`' aggregate shape (`ratingAvg`, `tripCount`, `punctualityScore`), over extending `users`. Reasoning — symmetry with the existing `driver_profiles` write/recompute pattern (`driver_rates_rider` ratings now have a real write target, computed by the same pure `computeRatingAggregate` function `packages/domain/src/rating/rating-aggregate.ts` applies to driver aggregates); churn isolation (rewritten on every new rating, kept off `users`, the identity table read on every authenticated request); optionality (a one-to-one row created lazily on a user's first rating/trip as a rider, rather than nullable aggregate columns on every user regardless of whether they've ever ridden). Full reasoning in the table's own doc comment and `docs/domain/model.md`.

Rating aggregation (`ratings.service.ts`'s `recomputeDriverAggregates`/`recomputeRiderAggregates`) always recomputes from every rating a user has received, never increments/decrements — correct even if a rating is ever later changed or removed by a future moderation action (out of scope here). The actual math is a pure function, `packages/domain/src/rating/rating-aggregate.ts` (`computeRatingAggregate`), mirroring the existing state-machine-module pattern; `punctualityScore` is computed only over ratings that actually set the optional `punctualityFlag`, so a rater who skipped it doesn't silently count as "not punctual" (a small correctness fix over the pre-Phase-9 inline logic, made while building the aggregation mechanism fresh, since none existed before). Trust-tier computation (`packages/domain/src/rating/trust-tier.ts`, `computeTrustTier`) is pure, unit-tested logic: "Nouveau" below 5 trips regardless of rating/tenure; "Top VAYA" only once trip count (≥20), rating average (≥4.7), and account age (≥60 days) all independently clear their thresholds; "Confiance" otherwise — VAYA's own naming, not BlaBlaCar's Expert/Ambassador labels. The 24h rating-submission window is also pure logic (`packages/domain/src/rating/rating-window.ts`, `isWithinRatingWindow`, inclusive at the exact boundary), anchored to a new `trips.completedAt` column (additive, nullable).

API: `POST /trips/:id/ratings` (tripId now in the URL, not the body — `packages/validation/src/ratings.ts` updated to match) enforces one rating per `(tripId, raterUserId)` and the 24h window server-side, both as 409s (structurally-invalid input is a 400 via the existing Zod schema); `GET /users/:id/trust-summary` returns the public-safe `{tier, ratingAvg, tripCount, punctualityScore}` shape for whichever of driver/rider reputations the user has — never raw comment text, in either direction, to anyone. The pre-Phase-9 `POST /ratings` and `GET /users/:id/ratings-summary` endpoints were replaced outright (nothing in mobile ever called them yet, verified) rather than kept alongside the new spec-correct ones, avoiding a half-built dual mechanism. `trip_completed` (already schema-defined, never dispatched before this phase) is reused as the rating-prompt push event rather than adding a new event type, per the phase doc's explicit option.

Mobile: new `StarRatingInput` design-system primitive (no equivalent existed — `ReviewCard` only ever displayed stars) and `Chip` gained an optional `onPress`/`selected` pair so a tappable punctuality chip no longer needs local raw-`TouchableOpacity` styling (the exact pattern the old `bookings/settlement.tsx` had improvised). `RatingPromptSheet` (`apps/mobile/src/features/ratings`) is a `BottomSheet`-based sheet reachable from `bookings/settlement.tsx` (which now fetches the real trip via `bookingId`, best-effort-completes it on arrival, and shows the sheet instead of its old dead "Terminer" button wired to nothing) and from a new global `RatingPromptBridge` mounted at the app root (`app/_layout.tsx`, same placement as Phase 7/8's `NotificationBridge`) that polls `GET /trips/pending-rating` once per cold start — the "re-surfaced once on next app open if unsubmitted" behavior, since this app has no local-notification-scheduling infrastructure for a true reminder. **Deviation from the phase doc's literal wording, documented and deliberate**: the trust-tier badge is wired into `search/trust.tsx` (as specified) and into `search/cluster.tsx`'s recommended-driver CTA, not `search/results.tsx` — verified that `results.tsx` only ever renders anonymous cluster counts with no per-driver identity on screen at all (`cluster.tsx` is where a specific driver is actually named, i.e. this app's real "result card"). All 4 analytics events (`rating_prompted`, `rating_submitted`, `rating_window_expired`, `trust_tier_shown`) fire via the existing `trackEvent` hook; `rating_window_expired` is necessarily a best-effort, session-scoped signal (documented in `RatingPromptBridge`'s doc comment) given the same thin dev-only analytics stub every other phase has used.

Tests: unit tests for trust-tier computation across trip-count/rating/tenure combinations, the 24h window boundary (inclusive/exclusive), and rating-aggregate math (`packages/domain/src/rating/__tests__`); a trip-status-transition unit test covering the new `completed`-from-anywhere edges; mobile helper unit tests (`ratingHelpers.test.ts`) for submission validation/trimming and the trust-tier-badge mapping; a real-Postgres integration test (`apps/api/src/modules/trips/__tests__/trips-ratings.integration.test.ts`) covering the full lifecycle end-to-end — accept → complete (by either party, rejected for a stranger) → both-direction ratings → duplicate rejected → aggregates recomputed on both `driver_profiles` and the new `rider_profiles` → visible via `getTrustSummary` on the other party's next lookup — plus a second test proving a backdated-past-window rating is rejected and no longer surfaced as pending.

**Phase 7 notes:** New `apps/api/src/modules/notifications` module (`registerPushToken`/`createNotification`/`listNotifications`/`markNotificationRead`/`dispatchPushForNotification`) plus a new `device_tokens` table (migration `0006_greedy_hedge_knight.sql`) — one row per (user, device), `token` globally unique so a re-registration updates in place. ## Sequencing logic

- **Phases 1-3** are foundation/infrastructure: fix what's broken, build the missing interaction-layer primitives, make maps real. Nothing product-shaped ships yet, but everything after depends on this being solid.
- **Phases 4-6** are the two hardest, highest-leverage systems the task brief calls out explicitly: the ride engine (stops) and pricing. These are NOW-horizon because they're the product's core marketplace mechanics, not because they're easy — they're High complexity and should not be rushed.
- **Phase 7** (notifications) sits at the NOW/NEXT boundary: it's needed to make booking events actually felt by users, and several NEXT-phase features (messaging, ratings, recurring rides) depend on its delivery mechanism.
- **Phases 8-11** are NEXT: they round out the marketplace (communication, trust, cancellation, retention) once the core loop (search → match → stop-select → price → book) is solid.
- **Phase 12** is SCALE: explicitly trigger-based, not calendar-based. Do not start it early.
