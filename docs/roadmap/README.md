# VAYA Implementation Roadmap

This is the status tracker and index for the phased roadmap produced by the 2026-08-19 codebase audit (`docs/product/audit.md`). Each phase is independently understandable and sized to be executable in one Claude Code session — a future session should be able to say **"Implement Phase N"** and act on that phase's file alone, without rediscovering the product from scratch.

## How to use this document

- Read `docs/product/audit.md`, `docs/domain/model.md`, `docs/domain/ride-engine.md`, and `docs/domain/pricing.md` once, at the start of a roadmap session, for the shared context every phase assumes.
- Each phase file (`phase-NN-slug.md`) is self-contained: objective, prerequisites, exact scope, flows, screens, UX behavior, design-system work, frontend/backend/database/API changes, business rules, testing, analytics, Definition of Done, dependencies, risks, complexity.
- Update the status table below as phases complete — this is the single source of truth for "what's done."

**Phase 7 notes:** New `apps/api/src/modules/notifications` module (`registerPushToken`/`createNotification`/`listNotifications`/`markNotificationRead`/`dispatchPushForNotification`) plus a new `device_tokens` table (migration `0006_greedy_hedge_knight.sql`) — one row per (user, device), `token` globally unique so a re-registration updates in place. First (and, per the phase's explicit scope, only) background job queue in this codebase: `apps/api/src/lib/queue.ts` wraps a single BullMQ `notification-dispatch` queue, consumed by one standalone worker process (`apps/api/src/worker.ts`, `pnpm --filter @vaya/api worker`) — never a general multi-queue framework. The queue's Redis connection is a second `ioredis` client pointed at the same `REDIS_URL` as `lib/cache.ts`, not a second Redis deployment; BullMQ requires `maxRetriesPerRequest: null`, incompatible with `cache.ts`'s bounded-retry client, so they can't literally share one connection object — full reasoning in `lib/queue.ts`'s doc comment. Push send is a direct HTTP call to Expo's push endpoint (`apps/api/src/modules/notifications/expo-push.ts`) rather than `expo-server-sdk`, kept dependency-free since this dispatch path only needs a plain send for 3 event types. `bookings.service.ts`'s `createBooking`/`acceptBooking`/`declineBooking` each gained one `notifyBestEffort(...)` call after their existing logic (Phase 1's atomic seat-accounting in `acceptBooking`/`cancelBooking` untouched) — creates the in-app `notifications` row and enqueues dispatch, wrapped so neither a row-insert failure nor an enqueue failure can ever fail the triggering booking action; verified with a real-Postgres-and-Redis integration test that mocks only the Expo HTTP call (`apps/api/src/modules/bookings/__tests__/bookings-notifications.integration.test.ts`) and a mocked-DB unit test of the dispatch worker itself (`apps/api/src/modules/notifications/__tests__/notification-dispatch.worker.test.ts`). Mobile: `expo-notifications` added (`~0.32.17`, the `sdk-54` dist-tag); new `apps/mobile/src/services/notifications/` (token registration, permission-prompt timing, foreground-Toast + tap-deep-link wiring, notification copy) and `apps/mobile/app/notifications/index.tsx` (minimal inbox — list, unread indicator via `Badge`, mark-as-read on tap; a small `Row`/`Text`/`Icon`/`Badge` composition per the phase doc, no new design-system primitive). Push permission is requested contextually — after a driver's first successful ride publish (`driver/publish.tsx`) or a passenger's first successful booking request (`search/trust.tsx`), never on cold start — and at most once per install (a SecureStore flag gates it, verified by a source-level regression test since there's still no RN component-rendering harness in this repo, same gap Phase 1's mock-data regression tests already documented). Deep-linking is scoped to exactly the 3 dispatched event types, all currently resolving to the existing `(tabs)/trips` screen — a dedicated driver "review this request" screen doesn't exist anywhere in this codebase yet (verified; a real gap, not built here, out of this phase's scope). All 4 analytics events (`push_permission_granted`/`denied`, `notification_delivered`/`notification_tapped`) fire via the existing `trackEvent` hook. **Deferred, real external-service setup this environment cannot complete** (same category as Phase 3's Google Maps key and Android verification note): live push delivery to a physical device requires actual Expo/EAS push credentials (an EAS `projectId`, APNs/FCM certificates) this sandboxed environment has none of — the code path (token registration → queue → Expo push HTTP call) is wired and tested with the real HTTP call mocked, but **on-device push delivery has not been, and cannot yet be, manually verified**; budget that as an explicit follow-up step before this ships to real users.

**Phase 6 notes:** `packages/domain/src/pricing/compute-suggested-price.ts`'s `computeSuggestedPrice(distanceKm, durationMin, config, {isEstimate})` is a pure function (unit-tested, zero I/O) producing `{min, recommended, max}` from `recommended = baseRatePerKm × distanceKm + timeComponentPerMin × durationMin`, an absolute floor (`ABSOLUTE_MIN_CONTRIBUTION_DT = 4`) for short rides, and a widened multiplier spread when the route came from the haversine fallback. New `pricing_configs` table (migration `0005_moaning_spiral.sql`), seeded with one active `national` row — the `base_rate_per_km`/`time_component_per_min` derivation is documented in `docs/domain/pricing.md`'s "Rate derivation (Phase 6, first-cut)" section and flagged there and in Open Decision #2 below as first-cut, pending business confirmation. `platformFeeRate` defaults to 0 and is not read anywhere — mechanism only, not activated, per the phase's explicit scope boundary. `POST /rides` now makes `contributionPerSeat` optional (server defaults to `recommended` when omitted) and returns the computed `{min, recommended, max}` plus `routeIsEstimate` alongside the created ride; a new `PATCH /rides/:rideId` (draft-only) lets the driver commit an adjusted price, independently re-deriving and re-validating the bound server-side both times — a direct API call with an out-of-bounds value is rejected with a clear 400 either way, verified by a real-Postgres/real-OSRM integration test (`apps/api/src/modules/rides/__tests__/rides-pricing.integration.test.ts`) and by the existing `tests/e2e` core-loop suite still passing unchanged. **Where the literal `[min, max]` check lives** deviates slightly from the phase brief's wording: it's in `rides.service.ts`, not the static Zod schema in `packages/validation` (a schema without DB/OSRM access can't know a route-dependent bound) — full reasoning in `docs/domain/pricing.md`'s Implementation note. `apps/api/src/db/seed.ts`'s seeded `routes`/`rides`/`bookings` pricing is now entirely formula-derived from real OSRM geometry (the "derive, don't hand-type" backfill option, not the "keep as documented override" one) — one source of truth, not two silently disagreeing. **Phase 5 notes:** `matching.service.ts`'s `scoreCandidates` now fetches each candidate ride's driver-selected `route_stops` in one batched query and ranks them by walk-distance via a new pure `rankStopsByWalkDistance` function (unit-tested without any DB/OSRM dependency, mirroring `stop-candidates.service.ts`'s own pure-function testing discipline), filtered to `WIDE_PICKUP_RADIUS_M`. **Zero-viable-stops decision** (a real product decision the phase file asked to make explicitly, not skip): a ride with real stops but none walkable for the passenger is *included* in results flagged `pickupViable: false`, not silently excluded — this keeps the `pickup_no_viable_stop` analytics event observable through the existing thin mobile `trackEvent` hook (no second, server-side analytics mechanism needed) while `search/cluster.tsx` still never renders or lets a passenger tap into a non-viable result, so the "never offer an impossible pickup" guarantee holds at the UI layer regardless. Full reasoning: `docs/domain/ride-engine.md`'s "Implementation note (Phase 5)". `search/pickup-point.tsx` — the single worst finding in the original audit (`PX_PER_DEGREE = 9000`, a fixed-degrees-per-pixel projection with no real geocoordinates behind it at all) — is fully rebuilt: real `MapCanvas` + numbered stop pins, closest stop pre-selected by default, `BottomSheet` for stop detail, honest `EmptyState` when zero stops are in range. `bookings.pickup_stop_id` (nullable FK → `route_stops`, `ON DELETE SET NULL`, migration `0004_common_bill_hollister.sql`) is enforced server-side in `bookings.service.ts`: a ride with any selected stops requires a valid same-ride `pickupStopId` and rejects free-form coordinates (400); a ride with zero stops keeps the old free-form flow working unchanged. **Genuinely verified:** unit tests for the ranking/viability pure functions and the mobile stop-selection helpers; an integration test against real Postgres covering the cross-ride-stopId rejection, the free-form-rejected-for-stopped-rides rule, and the legacy-ride-still-works case; and — the first real core-loop E2E coverage `tests/e2e` has ever had — a Playwright suite (`search-to-booking.api.test.ts`) exercising the actual HTTP flow end-to-end against a live server, real Postgres, and real docker-composed OSRM (driver onboarding → ride creation → real OSRM-backed candidate generation → stop selection → publish → passenger matching search asserting `rankedStops`/`pickupViable` → booking with `pickupStopId` → both rejection cases → legacy free-form booking), all 8 tests (health-check + new suite) passing against the real stack. `explore.tsx`'s pre-search "adjust pickup on map" entry point (which called the old fake screen before any ride was even selected) was removed rather than left pointing at a screen that now requires a `rideId` it can't supply — a necessary consequence of the scope change, not scope creep.

**Phase 4 notes:** the design doc (`docs/domain/ride-engine.md`) called for road class straight from OSRM's `nearest` response; verified against the live docker-composed OSRM instance that this deployment's `/nearest` and `/route` responses carry no way-class tag at all (neither service returns a `classes` field). Implemented instead: a local-speed classifier fed by `/route`'s `annotations=true` output (genuinely real per-segment data, not a heuristic on names) — see `stop-candidates.service.ts`'s `classifyRoadSpeed` doc comment and the corresponding note added to `docs/domain/ride-engine.md`. Verified end-to-end against real OSRM + real Postgres (integration test, plus a manual run against 3 real Tunisian routes spanning urban/suburban/intercity — the intercity Tunis→Hammamet run, which crosses the A1, correctly rejected 2 of 68 sampled points as motorway-class). Ride creation now starts as `draft` and a new `POST /rides/:id/publish` transitions to `published` (reusing the existing, previously-unused `draft` state and `canTransitionRideStatus` — not a new state machine), since candidate-stop generation needs a ride id and a computed `routePolyline` to exist before the driver's final publish action; mobile's `publish.tsx` drives both steps in one continuous flow so this is invisible to the driver.

## Sequencing logic

- **Phases 1-3** are foundation/infrastructure: fix what's broken, build the missing interaction-layer primitives, make maps real. Nothing product-shaped ships yet, but everything after depends on this being solid.
- **Phases 4-6** are the two hardest, highest-leverage systems the task brief calls out explicitly: the ride engine (stops) and pricing. These are NOW-horizon because they're the product's core marketplace mechanics, not because they're easy — they're High complexity and should not be rushed.
- **Phase 7** (notifications) sits at the NOW/NEXT boundary: it's needed to make booking events actually felt by users, and several NEXT-phase features (messaging, ratings, recurring rides) depend on its delivery mechanism.
- **Phases 8-11** are NEXT: they round out the marketplace (communication, trust, cancellation, retention) once the core loop (search → match → stop-select → price → book) is solid.
- **Phase 12** is SCALE: explicitly trigger-based, not calendar-based. Do not start it early.

## Known technical debt (carried forward from the audit, not yet phase-assigned beyond what's listed above)

- `apps/mobile/src/mocks/seed-data.ts` usage should shrink to legitimate test fixtures only as Phase 1 and later phases wire real data through; if any screen still imports it for production rendering after Phase 5, that's a regression.
- i18n: no `en` locale exists despite the type system allowing it; central `i18n.ts` wiring wasn't confirmed during the audit — verify early in any phase touching new user-facing copy.
- `tests/e2e` has only a health-check test; Phase 5's Definition of Done adds the first real E2E flow coverage (search→book) — extend E2E coverage opportunistically in every phase touching the core loop rather than batching it into one future "add tests" phase.
- The rider-reputation storage question (flagged in Phase 9) is a genuinely open design decision, not resolved by this roadmap.

## Open decisions (need a human call, not an engineering default)

1. **Product naming**: the app currently renders as "arc." on the landing screen (`apps/mobile/app/index.tsx`) while the codebase, CLAUDE.md, and this roadmap all say "VAYA." Resolve which is the real product name before it propagates further, or confirm "arc." is an intentional sub-brand/wordmark and document why.
2. **`base_rate_per_km`** (Phase 6): **first-cut value now in place (`0.25` DT/km, `time_component_per_min = 0.08`), pending business confirmation** — not still an open blocker. Derived autonomously during the Phase 6 session (Tunisian fuel price × typical compact-car consumption × a cost-sharing markup over pure fuel cost, cross-checked against this codebase's own pre-existing hand-authored route pricing) since no human was available to consult; full derivation and reasoning in `docs/domain/pricing.md`'s "Rate derivation (Phase 6, first-cut)" section. Treat as replaceable the moment real Tunisian market/survey data exists — do not treat its presence in `pricing_configs` as a settled business decision.
3. **Platform fee activation** (Phase 6, `docs/domain/pricing.md`): mechanism will exist, defaulted off. Activating it is a monetization decision for the user to make explicitly.
4. **Cancellation policy consequences without a payment system** (Phase 10): VAYA has no payments yet, so "refund" doesn't apply — needs an explicit reputation-based policy design.
5. **Dark mode**: no dark palette exists in the design system today; not assumed as a requirement — confirm whether it's in scope before any phase builds one.
6. **Messaging moderation/reporting** (Phase 8): flagged as a near-term follow-up risk, not scoped into Phase 8 itself — decide whether it should be pulled into Phase 8 or tracked as its own future phase.
