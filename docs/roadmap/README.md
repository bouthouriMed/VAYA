# VAYA Implementation Roadmap

This is the status tracker and index for the phased roadmap produced by the 2026-08-19 codebase audit (`docs/product/audit.md`). Each phase is independently understandable and sized to be executable in one Claude Code session — a future session should be able to say **"Implement Phase N"** and act on that phase's file alone, without rediscovering the product from scratch.

## How to use this document

- Read `docs/product/audit.md`, `docs/domain/model.md`, `docs/domain/ride-engine.md`, and `docs/domain/pricing.md` once, at the start of a roadmap session, for the shared context every phase assumes.
- Each phase file (`phase-NN-slug.md`) is self-contained: objective, prerequisites, exact scope, flows, screens, UX behavior, design-system work, frontend/backend/database/API changes, business rules, testing, analytics, Definition of Done, dependencies, risks, complexity.
- Update the status table below as phases complete — this is the single source of truth for "what's done."

**Phase 9 notes:** Closed the loop on the already-correctly-shaped `ratings` table with a real submission flow, aggregation, and trust-tier surfacing. **Necessary scope addition, verified before building (not assumed from the phase doc)**: this codebase had no trip-completion mechanism at all — confirmed directly (no caller of `canTransitionTripStatus` existed anywhere outside `packages/domain`'s own tests before this phase; Phase 8's notes above already flagged this). Added the minimal trigger only: `POST /trips/:id/complete` (new `apps/api/src/modules/trips` module) transitions a trip to `completed` via `packages/domain`'s state machine, which now allows a direct `completed` edge from every non-terminal trip status (`trip-status.ts`), not only from `arriving` — since this app's trip-progress screens (`bookings/pending → pickup → live → settlement`) are still a presentational mock with no live position feed driving them through the intermediate statuses one at a time. Deliberately callable by **either** trip party (not driver-only as a literal reading of the phase doc suggested): there is still no driver-side trip-execution screen anywhere in this codebase, so driver-only would leave the endpoint uncallable from any real screen; mirrors `bookings.service.ts`'s existing `cancelBooking`, which already lets either party trigger a status transition. Completing a trip also transitions its `booking.status` to `completed` (another existing-but-never-set schema value) and recomputes both parties' `tripCount` from `trips` directly (not an incremented counter) — a second, related gap this phase found: `driver_profiles.tripCount` was previously written only by `seed.ts` and never updated by any real trip.

**Rider-reputation storage decision** (this phase's other required, previously-open call): implemented a dedicated `rider_profiles` table (migration `0008_yellow_shen.sql`) mirroring `driver_profiles`' aggregate shape (`ratingAvg`, `tripCount`, `punctualityScore`), over extending `users`. Reasoning — symmetry with the existing `driver_profiles` write/recompute pattern (`driver_rates_rider` ratings now have a real write target, computed by the same pure `computeRatingAggregate` function `packages/domain/src/rating/rating-aggregate.ts` applies to driver aggregates); churn isolation (rewritten on every new rating, kept off `users`, the identity table read on every authenticated request); optionality (a one-to-one row created lazily on a user's first rating/trip as a rider, rather than nullable aggregate columns on every user regardless of whether they've ever ridden). Full reasoning in the table's own doc comment and `docs/domain/model.md`.

Rating aggregation (`ratings.service.ts`'s `recomputeDriverAggregates`/`recomputeRiderAggregates`) always recomputes from every rating a user has received, never increments/decrements — correct even if a rating is ever later changed or removed by a future moderation action (out of scope here). The actual math is a pure function, `packages/domain/src/rating/rating-aggregate.ts` (`computeRatingAggregate`), mirroring the existing state-machine-module pattern; `punctualityScore` is computed only over ratings that actually set the optional `punctualityFlag`, so a rater who skipped it doesn't silently count as "not punctual" (a small correctness fix over the pre-Phase-9 inline logic, made while building the aggregation mechanism fresh, since none existed before). Trust-tier computation (`packages/domain/src/rating/trust-tier.ts`, `computeTrustTier`) is pure, unit-tested logic: "Nouveau" below 5 trips regardless of rating/tenure; "Top VAYA" only once trip count (≥20), rating average (≥4.7), and account age (≥60 days) all independently clear their thresholds; "Confiance" otherwise — VAYA's own naming, not BlaBlaCar's Expert/Ambassador labels. The 24h rating-submission window is also pure logic (`packages/domain/src/rating/rating-window.ts`, `isWithinRatingWindow`, inclusive at the exact boundary), anchored to a new `trips.completedAt` column (additive, nullable).

API: `POST /trips/:id/ratings` (tripId now in the URL, not the body — `packages/validation/src/ratings.ts` updated to match) enforces one rating per `(tripId, raterUserId)` and the 24h window server-side, both as 409s (structurally-invalid input is a 400 via the existing Zod schema); `GET /users/:id/trust-summary` returns the public-safe `{tier, ratingAvg, tripCount, punctualityScore}` shape for whichever of driver/rider reputations the user has — never raw comment text, in either direction, to anyone. The pre-Phase-9 `POST /ratings` and `GET /users/:id/ratings-summary` endpoints were replaced outright (nothing in mobile ever called them yet, verified) rather than kept alongside the new spec-correct ones, avoiding a half-built dual mechanism. `trip_completed` (already schema-defined, never dispatched before this phase) is reused as the rating-prompt push event rather than adding a new event type, per the phase doc's explicit option.

Mobile: new `StarRatingInput` design-system primitive (no equivalent existed — `ReviewCard` only ever displayed stars) and `Chip` gained an optional `onPress`/`selected` pair so a tappable punctuality chip no longer needs local raw-`TouchableOpacity` styling (the exact pattern the old `bookings/settlement.tsx` had improvised). `RatingPromptSheet` (`apps/mobile/src/features/ratings`) is a `BottomSheet`-based sheet reachable from `bookings/settlement.tsx` (which now fetches the real trip via `bookingId`, best-effort-completes it on arrival, and shows the sheet instead of its old dead "Terminer" button wired to nothing) and from a new global `RatingPromptBridge` mounted at the app root (`app/_layout.tsx`, same placement as Phase 7/8's `NotificationBridge`) that polls `GET /trips/pending-rating` once per cold start — the "re-surfaced once on next app open if unsubmitted" behavior, since this app has no local-notification-scheduling infrastructure for a true reminder. **Deviation from the phase doc's literal wording, documented and deliberate**: the trust-tier badge is wired into `search/trust.tsx` (as specified) and into `search/cluster.tsx`'s recommended-driver CTA, not `search/results.tsx` — verified that `results.tsx` only ever renders anonymous cluster counts with no per-driver identity on screen at all (`cluster.tsx` is where a specific driver is actually named, i.e. this app's real "result card"). All 4 analytics events (`rating_prompted`, `rating_submitted`, `rating_window_expired`, `trust_tier_shown`) fire via the existing `trackEvent` hook; `rating_window_expired` is necessarily a best-effort, session-scoped signal (documented in `RatingPromptBridge`'s doc comment) given the same thin dev-only analytics stub every other phase has used.

## Sequencing logic

- **Phases 1-3** are foundation/infrastructure: fix what's broken, build the missing interaction-layer primitives, make maps real. Nothing product-shaped ships yet, but everything after depends on this being solid.
- **Phases 4-6** are the two hardest, highest-leverage systems the task brief calls out explicitly: the ride engine (stops) and pricing. These are NOW-horizon because they're the product's core marketplace mechanics, not because they're easy — they're High complexity and should not be rushed.
- **Phase 7** (notifications) sits at the NOW/NEXT boundary: it's needed to make booking events actually felt by users, and several NEXT-phase features (messaging, ratings, recurring rides) depend on its delivery mechanism.
- **Phases 8-11** are NEXT: they round out the marketplace (communication, trust, cancellation, retention) once the core loop (search → match → stop-select → price → book) is solid.
- **Phase 12** is SCALE: explicitly trigger-based, not calendar-based. Do not start it early.

## Open decisions (need a human call, not an engineering default)

1. **Product naming**: the app currently renders as "arc." on the landing screen (`apps/mobile/app/index.tsx`) while the codebase, CLAUDE.md, and this roadmap all say "VAYA." Resolve which is the real product name before it propagates further, or confirm "arc." is an intentional sub-brand/wordmark and document why.
2. **`base_rate_per_km`** (Phase 6): **first-cut value now in place (`0.25` DT/km, `time_component_per_min = 0.08`), pending business confirmation** — not still an open blocker. Derived autonomously during the Phase 6 session (Tunisian fuel price × typical compact-car consumption × a cost-sharing markup over pure fuel cost, cross-checked against this codebase's own pre-existing hand-authored route pricing) since no human was available to consult; full derivation and reasoning in `docs/domain/pricing.md`'s "Rate derivation (Phase 6, first-cut)" section. Treat as replaceable the moment real Tunisian market/survey data exists — do not treat its presence in `pricing_configs` as a settled business decision.
3. **Platform fee activation** (Phase 6, `docs/domain/pricing.md`): mechanism will exist, defaulted off. Activating it is a monetization decision for the user to make explicitly.
4. **Cancellation policy consequences without a payment system** (Phase 10): VAYA has no payments yet, so "refund" doesn't apply — needs an explicit reputation-based policy design.
5. **Dark mode**: no dark palette exists in the design system today; not assumed as a requirement — confirm whether it's in scope before any phase builds one.
6. **Messaging moderation/reporting** (Phase 8): flagged as a near-term follow-up risk, not scoped into Phase 8 itself — decide whether it should be pulled into Phase 8 or tracked as its own future phase. **Still open as of Phase 8 shipping** (2026-08-19): Phase 8 implemented messaging exactly per its documented scope (two-party, text-only, time-bounded conversations) and deliberately did not add reporting/blocking/content moderation — this remains a real gap before opening messaging to production users at scale.
