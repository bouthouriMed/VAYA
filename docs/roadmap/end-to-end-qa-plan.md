## 4. Known external/manual blockers (mission section 30 — document, don't stop)

These cannot be resolved without something outside this environment:

1. **Live Google OAuth consent-screen round-trip** — needs a real interactive browser session signing into a real Google account; verified everything on this app's side of that boundary instead (see Section 1). Ask a real device/simulator user to tap "Continuer avec Google" on the landing screen and confirm they land signed-in on `/(tabs)/explore` with `me.email`/`me.authProvider === 'google'` populated.
2. **Google OAuth redirect port** — `GOOGLE_CALLBACK_URL=http://localhost:4000/...` is registered in Google Cloud Console exactly as given; the API now binds a second listener on port 4000 specifically to satisfy it (`server.ts`) without moving the whole API off :3000. This works for local/emulator testing. **For a physical device over LAN**, `localhost` won't resolve to the dev machine — the registered redirect URI (and `apps/mobile`'s effective API origin) would need to point at the host's LAN IP instead, the same category of constraint CLAUDE.md already documents for `API_BASE_URL` over Expo Go/LAN.
3. **Live push notification delivery** — Phase 7's dispatch path is fully implemented and tested against a mocked Expo push response; no real EAS project id / APNs / FCM credentials exist in this environment (pre-existing, documented blocker, unchanged by this pass).
4. **Android Google Maps API key** — pre-existing, documented blocker, unchanged by this pass.
5. **No on-device UI verification at all** — this pass's Google Sign-In button, notification bell, and profile row changes were verified via typecheck/lint/existing automated suites, not a running Expo app on a device/simulator (no such device is available in this sandboxed environment).

## 5b. Post-initial-pass fixes (same session, after live device testing)

- **Google callback couldn't reach the dev machine from a physical device.** `GOOGLE_CALLBACK_URL` pointed at `localhost`, which resolves to the phone itself, not the dev machine, once testing moved off the simulator. A LAN IP doesn't work either — Google's redirect-URI validator rejects raw private IPs outright ("must end in a public top-level domain"). Fixed with a free Cloudflare quick tunnel (`npx cloudflared tunnel --url http://localhost:4000`) giving a real public HTTPS domain, registered in GCP. Also fixed a related bug this exposed: `server.ts` was deriving its local callback-listener port from `GOOGLE_CALLBACK_URL`'s own port, which is wrong for a tunnel URL (implicit 443, not the real local port) — split into a dedicated `GOOGLE_OAUTH_CALLBACK_PORT` env var, decoupled from the URL string.
- **"Safari cannot open the page" after Google consent.** The backend redirected back to a hardcoded `vaya://auth/google` deep link, but Expo Go (used for this device testing) doesn't own that scheme — it listens on its own dynamic `exp://<host>:<port>/--/...` URL instead. Fixed by having the mobile client pass its real `Linking.createURL()` redirect URI to `/auth/google/start` as a query param, round-tripped through the signed `state` JWT (so it can't be tampered with) and used verbatim by `/auth/google/callback`. Verified end-to-end: user signed in successfully with a real Google account.
- **Profile UX refinement for a new Google-signed-in user** (no phone, no ratings yet): avatar's "Modifier la photo" text link replaced with a small camera-icon badge on the avatar itself; a "Nouveau sur Vaya" pill now fills that slot for zero-trip users (same slot the real trust-tier pill uses once ratings exist); a small alert dot on the "Informations personnelles" row plus a clear "Ajouter et vérifier" chip (replacing a greyed-out "Non renseigné") surface the missing phone number. Built a real, tested add-phone flow: new authenticated `POST /users/me/phone/request-otp` / `POST /users/me/phone/verify` endpoints attach a verified phone to the current session's user (distinct from `/auth/otp/*`, which signs a *new* session in) — rejects a phone already claimed by another user (409), 4 new integration tests against real Postgres.
- Full suites re-verified after all of the above: 107 API tests / 19 files, 180 mobile tests / 27 files, all passing.
